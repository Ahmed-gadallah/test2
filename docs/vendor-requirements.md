# متطلبات ربط تطبيق صيدليات زاد مع نظام الـ ERP

**الموجّه إلى:** فريق تطوير نظام الـ ERP / POS
**الغرض:** ربط تطبيق العملاء (Android / iOS) ببيانات Workspace 0 (صيدليات زاد) عبر API آمن.
**الحالة الحالية:** التطبيق والـ backend جاهزان ويعملان على بيانات تجريبية. لا يوجد حاليًا API موثّق لنظامكم، وميزة "موافقة العميل على استبدال النقاط" غير موجودة في النظام.

> مبدأ أساسي: نظام الـ ERP هو المرجع الوحيد للعملاء والفواتير وكل حسابات النقاط. التطبيق لا يحسب ولا يخصم أي نقاط؛ يعرض فقط ما يرجعه الـ API، ويرسل قرار العميل.

---

## أولًا: مطلوب فورًا (قبل أي تطوير)

| # | المطلوب | ملاحظات |
|---|---|---|
| 1 | **توثيق أي API موجود حاليًا** (OpenAPI / Swagger / Postman) | أو تأكيد كتابي بعدم وجود API |
| 2 | **شرح الجداول:** `user_token`, `workspace_integration_0`, `integration_profile` | هل هي واجهة تكامل قائمة يمكن استخدامها؟ |
| 3 | **بيئة اختبار (Staging)** منفصلة عن الإنتاج + بيانات اعتماد اختبار | ببيانات تجريبية، **بدون بيانات عملاء حقيقية** |
| 4 | **طريقة التوثيق بين الأنظمة** (Server-to-Server) | نقترح OAuth2 Client Credentials أو API Key + قائمة IP مسموحة، عبر HTTPS فقط، ومقيّدة بـ Workspace 0 فقط |
| 5 | حدود الطلبات (Rate limits)، مستوى الخدمة (SLA)، نوافذ الصيانة، سياسة الإصدارات (Versioning)، وشكل رسائل الأخطاء | |
| 6 | **مسؤول تقني** للتواصل + **جدول زمني** لكل مرحلة أدناه | |

## ثانيًا: المرحلة 1 — واجهات القراءة (تتيح تشغيل تجريبي ببيانات حقيقية)

| # | الواجهة | المدخلات | المخرجات المطلوبة |
|---|---|---|---|
| 1 | البحث عن عميل برقم الجوال | رقم جوال (يُطبّع لصيغة `+9665XXXXXXXX`) | **كل** السجلات المطابقة (وليس الأول فقط): رقم العميل، الاسم، الجوال، وعلامة توضح هل الحساب فردي أم مؤسسي/تأمين |
| 2 | بيانات العميل | رقم العميل | الاسم، الجوال، رقم العميل (بدون رقم الهوية) |
| 3 | رصيد النقاط | رقم العميل | الرصيد الحالي + وقت آخر تحديث |
| 4 | **سجل النقاط (منظّم)** | رقم العميل، Pagination | لكل حركة: النوع (مكتسبة/مستبدلة/مرتجع/تعديل يدوي)، عدد النقاط بالإشارة، الرصيد بعد الحركة، رقم الفاتورة، الفرع، التاريخ، السبب |
| 5 | قائمة الفواتير | رقم العميل، Pagination، فلتر الحالة | رقم الفاتورة الظاهر للعميل، التاريخ، الفرع، الإجمالي، الحالة |
| 6 | تفاصيل الفاتورة | رقم العميل + رقم الفاتورة | الأصناف (الاسم، الكمية، السعر، الخصومات، الضريبة)، المجاميع، النقاط المستخدمة والمكتسبة، طريقة الدفع. **يجب رفض الطلب إن كانت الفاتورة لعميل آخر** |
| 7 | قائمة الفروع | — | المعرّف، الاسم، المدينة |

**ملاحظات على البيانات الحالية (تحتاج حل من جهتكم):**

- سجل النقاط الحالي (`customer_timeline_0`) **نص حر (Markdown)** وليس حقولًا، ويبدأ من **2026-08-14** بينما الفواتير تبدأ من 2025-10-24، ويحتوي على **أسماء الكاشير**. نحتاج سجلًا منظّمًا، ويُفضّل استكمال التاريخ السابق أو تحديد تاريخ بداية رسمي.
- أي رقم فاتورة هو الظاهر للعميل على الإيصال: `orders_0.id` أم `uuid` أم رقم ZATCA (`icv`)؟
- أي حالات فواتير تظهر للعميل؟ (يوجد حوالي 58 ألف فاتورة بحالة `PENDING`؛ ما معناها؟)

## ثالثًا: المرحلة 2 — ميزة استبدال النقاط بموافقة العميل (تطوير جديد لديكم)

**الوضع الحالي:** الكاشير يطبّق خصم النقاط مباشرة والرصيد يتغير فورًا. لا يوجد "طلب معلّق" ولا موافقة.

**المطلوب:**

1. **في شاشة الكاشير (POS):** عند اختيار "استبدال نقاط"، يُنشأ **طلب استبدال معلّق** بدل الخصم المباشر، وتنتظر الشاشة رد العميل حتى انتهاء المهلة.
2. **كيان جديد `redemption_request`** بالحقول: معرّف فريد، العميل، الفرع، عدد النقاط، قيمة الخصم بالريال، الحالة، وقت الإنشاء، وقت الانتهاء.
   الحالات: `pending` ← `completed` / `rejected` / `expired` / `failed`.
3. **واجهات:**
    - جلب الطلبات المعلّقة لعميل.
    - جلب طلب بالمعرّف.
    - **إرسال قرار العميل (موافقة/رفض) مع `Idempotency-Key`**: تكرار نفس الطلب يرجع نفس النتيجة **ولا يخصم مرتين**.
4. **عند الموافقة:** نظامكم يتحقق من **الرصيد الفعلي** و**عدم انتهاء المهلة** ثم يخصم. التطبيق لا يخصم أبدًا.
5. **المهلة قابلة للضبط** (نقترح 2–3 دقائق).
6. **التعامل مع الطلبات المتزامنة** بأمان (طلبان لنفس العميل في نفس الوقت).
7. **سجل تدقيق** لكل طلب وحالته النهائية.
8. **وضع بديل في الـ POS** عندما لا يستطيع العميل الموافقة من التطبيق (القرار التجاري تحدده زاد، والتنفيذ لديكم).

## رابعًا: الإشعارات اللحظية (Webhooks)

نحتاج أن يرسل نظامكم أحداثًا إلى خادمنا (HTTPS، موقّعة بـ HMAC، مع إعادة المحاولة عند الفشل):

| الحدث | متى |
|---|---|
| `redemption.created` | عند إنشاء طلب استبدال معلّق (**الأهم**) |
| `redemption.updated` | عند اكتمال/رفض/انتهاء الطلب |
| `order.finished` | فاتورة جديدة (لإشعار "اكتسبت نقاط") |
| `order.refunded` | مرتجع كلي/جزئي |
| `points.adjusted` | تعديل يدوي على النقاط |

إن لم تتوفر Webhooks، نحتاج واجهة لجلب الطلبات المعلّقة نستطيع استدعاءها كل بضع ثوانٍ.

## خامسًا: قواعد البرنامج وأسئلة مفتوحة

**قواعد معتمدة من زاد:**

- الاكتساب: **نقطة واحدة لكل ريال**.
- الاستبدال: **كل 50 نقطة = 1 ريال، وبالريال الكامل فقط** (مضاعفات 50 نقطة).
- لا يوجد حاليًا ما يميّز الحسابات المؤسسية/التأمين عن العملاء الأفراد.

**مطلوب منكم توضيحه — اختلاف بين القاعدة والبيانات الفعلية:**

تحليل فواتير آخر 30 يومًا (118,674 فاتورة مكتملة حصلت على نقاط، `orders_0`):

| المقارنة | نسبة الفواتير المطابقة |
|---|---|
| النقاط = المبلغ المدفوع فعليًا (`total`) | 50% |
| النقاط = المدفوع + قيمة النقاط المستخدمة (`total + point_to_cash`) | 58.8% |
| فواتير فيها استبدال (20,342): النقاط على المدفوع فقط | 6.2% |
| نفس الفواتير: النقاط تشمل الجزء المدفوع بالنقاط | 57.6% |

1. **عند الاستبدال، يكتسب العميل نقاطًا على الجزء الذي دفعه بالنقاط** (مثال: دفع 49.60 ريال نقدًا + 8 ريال نقاط ← اكتسب 58 نقطة). الفرق في آخر 30 يومًا ≈ **506,308 نقطة (≈ 10,126 ريال)**. هل هذا مقصود؟ وإن لم يكن، نرجو تصحيحه.
2. **حوالي 40% من الفواتير لا تطابق أيًّا من الصيغتين.** ما الأساس الفعلي للحساب (قبل العروض؟ استثناء أصناف؟ قبل/بعد الضريبة؟ التقريب؟)
3. نحتاج **علامة (flag) في بيانات العميل** تميّز الحسابات المؤسسية/التأمين (مثال: الحساب `325439` يحمل أكثر من 60% من إجمالي النقاط)، حتى لا يتمكن من التسجيل في التطبيق.

*(الأرقام تقريبية بهامش ±1 نقطة ولا تحتسب الضريبة والعروض على مستوى الصنف؛ هي مؤشر وليست إثباتًا.)*

## سادسًا: جودة البيانات (مطلوب تنظيفها أو وضع قواعد لها)

- تنسيقات أرقام الجوال غير موحّدة (أطوال مختلفة، بدون `+`).
- **61 مجموعة** من سجلات عملاء مختلفة تشترك في نفس رقم الجوال (آخر 9 أرقام).
- **1,642** رقمًا لا يبدو رقم جوال سعودي (لن يتمكن أصحابها من استلام رمز التحقق).
- أسماء العملاء مُدخلة يدويًا وتحتوي أرقامًا وعبارات (مثل "اسم + أرقام عشوائية").

---

## سابعًا: الأمان والخصوصية (PDPL)

- HTTPS فقط، وبيانات الاعتماد لا تُرسل عبر البريد أو المحادثات.
- الوصول مقيّد بـ **Workspace 0 فقط**، وعدم إتاحة بيانات أي Workspace آخر.
- عدم إرجاع رقم الهوية أو أسماء الموظفين في واجهات العملاء.
- اتفاقية معالجة بيانات (DPA) بين الطرفين.

---

## ما سنقدّمه نحن لتسريع العمل

- **عقد مقترح جاهز** لشكل البيانات (Request/Response) مبني على جداولكم الحالية، نرسله لكم كملف منفصل. يمكنكم اعتماده أو التعديل عليه.
- عنوان الـ Webhook الخاص بنا ومفتاح التوقيع عند جاهزية بيئة الاختبار.
- عناوين IP الخاصة بخوادمنا لإضافتها للقائمة المسموحة.
- اختبارات تكامل آلية على بيئة الاختبار فور توفرها.
